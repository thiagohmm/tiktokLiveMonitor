# Plano v5 — Fila PIX via WhatsApp (WAHA + MinIO) no tiktokLiveMonitor

> Refinamento após mudanças de direção:
> 1. implementar em **branch separada**;
> 2. mídias ficam em **MinIO**;
> 3. ao usuário desconectar a live **ou fechar a página**, a live dele é desconectada e as mídias
>    da Fila PIX dele são apagadas;
> 4. se dois usuários monitoram a mesma live, um usuário sair **não pode** apagar as mídias do
>    outro nem derrubar o monitoramento enquanto houver outro usuário conectado.
>
> Refinamento adicional desta revisão:
> - monitoramento passa a ser identificado por **usuário + live** (anexo/detach com contagem de
>   usuários conectados);
> - o expurgo é **por usuário dono da sessão**, nunca global entre usuários;
> - `owner_user_id` é `TEXT` (UUID do Supabase Auth) e **sem FK para `auth.users`**, para não
>   quebrar o Postgres local do docker-compose.
>
> Contexto de execução: **Railway não é mais usado**; testes e operação acontecem via
> **docker-compose** (dev local e VPS).

## 1. Objetivo

Adicionar ao **tiktokLiveMonitor** (backend Go + frontend HTML/JS vanilla) uma **Fila PIX**:

1. Cada usuário autenticado pareia o próprio WhatsApp via QR code usando **WAHA**.
2. Clientes enviam mensagens e comprovantes PIX (JPG/PDF) pelo WhatsApp pareado.
3. Comprovantes ficam armazenados no **MinIO** e são apagados quando o usuário **desconecta a
   live ou fecha a página**.
4. Se dois usuários monitoram a mesma live, a saída de um usuário apaga somente as mídias dele;
   as mídias do outro usuário permanecem.
5. Mensagens de texto, metadados e histórico permanecem no Postgres; somente o objeto da mídia
   some.
6. O operador abre um item pendente, conversa com o cliente **somente por texto** e, ao terminar,
   clica em **Respondido**.
7. O número do cliente passa a aparecer no histórico, no padrão da fila de presentes existente.

**Não haverá migração para Java/Spring Boot.** WAHA e MinIO são APIs HTTP/S3 compatíveis;
o backend Go atual já possui HTTP server, Supabase Auth, Postgres e SSE.

## 2. Decisões consolidadas

**Restrição arquitetural obrigatória:** manter a arquitetura e a segurança existentes. A Fila PIX
é uma extensão dos pacotes atuais, não uma reescrita.

- Não trocar `net/http` por framework/router novo.
- Não trocar Supabase Auth, JWT Bearer + cookie HttpOnly, RBAC existente ou middleware atual.
- Não trocar Postgres/pgx/`database/sql` por ORM.
- Não alterar o modelo de RLS: frontend nunca acessa tabelas operacionais; todo dado passa pela API Go.
- Não criar segundo stream SSE nem autenticação paralela.
- Não expor WAHA/MinIO diretamente ao navegador.
- Rotas e comportamentos atuais permanecem compatíveis; novas rotas são aditivas.

| Tema | Decisão |
|---|---|
| Branch | Nova branch a partir de `lite-sem-ia`: `feature/fila-pix-waha` |
| Escopo | Multi-tenant: **cada usuário conecta seu próprio WhatsApp** |

## 3. Estado atual do projeto (fatos relevantes)

- Backend Go puro (`net/http`, `http.NewServeMux`), sem framework HTTP.
- Banco Postgres via `database/sql` + `pgx`; queries com `?` reescritos por `rebindQuery`.
- Entidades em `internal/model/entities.go`; interfaces em `internal/model/repository.go`;
  implementação em `internal/database/*.go`.
- IDs das tabelas operacionais são `BIGSERIAL`/Go `int64`.
- Timestamps são persistidos/retornados como strings RFC3339Nano (`sql.NullString` no scan).
- Migrações Go idempotentes ficam em `migratePostgres()` e são espelhadas em
  `supabase/migrations/`; o REVOKE para `anon/authenticated` fica só no arquivo SQL porque
  bancos de teste locais não têm esses papéis.
- Auth Supabase: JWT em `Authorization: Bearer` ou cookie `tlm_access_token`; `User.ID` é UUID
  string (`sub`). `auth.UserFromContext(ctx)` retorna `(*auth.User, bool)`.
- Se `AUTH_ENABLED=0`, o middleware cria usuário sintético sem ID; nesse modo dev-only, rotas
  Pix/monitoramento multiusuário devem responder `503` com erro de configuração em vez de operar
  com owner vazio.
- `auth.PublicPath()` libera apenas `/api/auth/*` e `/api/readiness`; o webhook WAHA deve ser
  adicionado lá explicitamente.
- SSE já existe em `GET /events`, via `auth.js:createEventStream()` (fetch + ReadableStream,
  com Bearer). Reutilizar; não criar outro cliente SSE.
- Não existe WhatsApp/WAHA/webhook/storage/upload hoje.
- O limite global de body é 1 MiB (`limitBody`), suficiente porque o webhook carrega só JSON
  com URL de mídia — o download binário acontece server-side no WAHA e o upload ao MinIO também
  acontece server-side.
- Hoje `handleDisconnect` chama `StopMonitoringLive(username)`; no `Manager`, `username=""` para
  todas as lives e não há noção de qual usuário autenticado está monitorando cada live.
- Para suportar dois usuários na mesma live, o monitoramento precisa virar um **anexo por usuário**:
  `AttachMonitoring(ownerUserID, username)` / `DetachMonitoring(ownerUserID, username)` com
  contagem de usuários conectados por live.
- O monitor interno de uma live só é encerrado quando o último usuário conectado nela sair.
- O Postgres local do docker-compose não é um Supabase completo; portanto as tabelas operacionais
  novas devem usar `owner_user_id TEXT` sem FK para `auth.users`.
- Fechamento de aba não executa handler REST normal de forma confiável; será usado
  `navigator.sendBeacon` no `pagehide`, autenticado pelo cookie HttpOnly existente.
- Recarregar a página (`navigation.type === 'reload'`) **não deve** disparar desconexão/expurgo.
- Docker de produção atual é VPS (`docker-compose.production.yml` + nginx), não Railway.

## 4. Protocolo WAHA — fatos verificados no código do filazap

Fontes verificadas:
- `filazap/backend/.../whatsapp/WahaPairingService.java`
- `filazap/backend/.../whatsapp/WahaWhatsAppGateway.java`
- `filazap/backend/.../whatsapp/WahaWhatsAppWebhookParser.java`
- `filazap/backend/.../whatsapp/WahaWebhookSignatureVerifier.java`
- `filazap/docs/07-whatsapp.md`

### 4.1 Autenticação e pairing

- Header WAHA: `X-Api-Key` (chave global do container).
- Criar/iniciar sessão: `POST {WAHA_URL}/api/sessions/`, body `{"name":"...","start":true}`.
  - `2xx` = criada; `400/409/422` = já existe. Tratar ambos como sucesso idempotente.
- QR: `GET {WAHA_URL}/api/{session}/auth/qr` → PNG.
  - Se já estiver conectado, WAHA pode não ter QR disponível; backend deve mapear erro para
    `409` com estado "já conectado" quando aplicável.
- Status: `GET {WAHA_URL}/api/sessions/{session}` → `{status, engine:{state}, me}`.
  - Conectado quando `status` ou `engine.state` for `CONNECTED`/`WORKING`, ou quando `me.phone`
    existir. Normalizar com uppercase antes de comparar.
  - `SCAN_QR_CODE`, `STARTING`, `FAILED`, `STOPPED` são estados transitórios/finais.
- Logout: `POST {WAHA_URL}/api/sessions/{session}/logout`.
- QR tem validade curta; o frontend deve renovar a imagem enquanto estiver em `scan_qr` e o
  backend deve tratar ausência temporária de QR sem derrubar a sessão.

### 4.2 Envio

- Texto: `POST {WAHA_URL}/api/sendText` com `{session, chatId, text}`.
- `chatId`: número em dígitos + `@c.us` (ex.: `5511999990001@c.us`).
  - Se já vier JID (`...@lid` ou `...@c.us`), passar intacto.
- Respostas de send variam por engine: id pode estar em `id`, `_data.id`, `key.id` ou `data.id`.
  Se não houver id, gerar `waha-local-<uuid>` e ainda persistir a mensagem — 2xx já significa
  que WAHA aceitou; lançar erro causaria reenvio duplicado.
- Não enviaremos mídia nesta fase.

### 4.3 Webhook

Envelope: `{event, session, me, payload, engine, ...}`.

- Assinatura: `X-Webhook-Hmac` = HMAC-SHA512 hex do **raw body** com `WAHA_WEBHOOK_SECRET`.
  - Aceitar opcionalmente prefixo `sha512=`.
  - Comparar em constant-time.
  - Falha fechada: ausente/inválido/secret vazio → `401`.
  - Header auxiliar: `X-Webhook-Hmac-Algorithm: sha512` (logar se vier diferente; não rejeitar
    só por ausência desse header auxiliar).
- Eventos:
  - `message` / `message.any` → mensagem.
  - `message.ack` → status de entrega; fora do escopo inicial, aceitar e ignorar com 200.
- Descartar:
  - `payload.fromMe == true` (eco das próprias mensagens).
  - `payload.from` com domínio `@g.us` (grupos).
- Normalização:
  - `@c.us` → extrair dígitos para `phone_e164`.
  - `@lid` → preservar como `whatsapp_jid` de envio; tentar resolver número via
    `GET /api/{session}/lids/{id}` (`pn`), mas falha é silenciosa.
  - Tipo: WAHA não envia `type`; derivar de `hasMedia` + `media.mimetype`.
    - `image/jpeg`/`image/jpg` → `image`
    - `application/pdf` → `document`
    - sem mídia → `text`
    - qualquer outro → `unsupported`
  - Timestamps podem vir em segundos, milissegundos ou float; normalizar para epoch seconds.
  - `payload.media.url` é URL absoluta; baixar com `X-Api-Key`, timeout 60s, limite 16 MB.
  - Dedup por `payload.id` (`whatsapp_message_id`).

## 5. Arquitetura alvo

### 5.0 Monitoramento multiusuário e expurgo por usuário

O backend atual gerencia lives por `live_name`. Para a regra de mídia, isso não basta: dois
usuários podem monitorar a mesma live e cada um pode ter sua própria Fila PIX.

Introduzir uma camada de anexos de monitoramento:

```go
type MonitorAttachmentStore interface {
    Attach(ownerUserID, liveName string) (attached bool, activeUsers int, err error)
    Detach(ownerUserID, liveName string) (detached bool, remainingUsers int, err error)
    DetachAll(ownerUserID string) (lives []string, err error)
}
```

Regras:

- `Attach(owner, live)` adiciona o usuário ao conjunto da live; se for o primeiro usuário,
  inicia/reativa o monitor daquela live.
- `Detach(owner, live)` remove só aquele usuário; se restarem usuários, o monitor continua.
- `DetachAll(owner)` remove o usuário de todas as lives ativas dele.
- O monitor interno (`monitor.Manager`) só recebe stop quando `remainingUsers == 0`.
- A store pode começar em memória, protegida por mutex, porque backend é uma instância única;
  em reinício, não há usuários anexados e não deve haver expurgo automático.
- `Detach` bem-sucedido sempre dispara `PurgeOwnerMedia(ownerUserID, reason)`, mesmo que o
  monitor da live continue ativo para outros usuários.

O handler de desconexão passa a usar o usuário autenticado:

```go
func (s *HTTPServer) handleDisconnect(w http.ResponseWriter, r *http.Request) {
    user, ok := auth.UserFromContext(r.Context())
    if !ok || user == nil || user.ID == "" {
        writeError(w, http.StatusUnauthorized, "unauthorized")
        return
    }
    username := r.URL.Query().Get("username")
    lives, err := s.controller.DetachMonitoring(user.ID, username)
    // após detach: go PurgeOwnerMedia(user.ID, "live disconnected")
}
```

Semântica:
- `username` preenchido → desanexa só aquela live do usuário.
- `username` vazio → desanexa o usuário de todas as lives ativas dele.
- Em ambos os casos, expurgo apenas do `ownerUserID` da requisição.

### Fechamento da página

- Frontend instala handler `pagehide` (ou fallback `beforeunload`) somente quando o usuário estiver
  com monitoramento ativo.
- Se `performance.getEntriesByType('navigation')[0].type === 'reload'`, não envia beacon.
- Em fechamento real, chama:

```js
navigator.sendBeacon(
  '/api/monitoring/beacon-disconnect',
  new Blob([JSON.stringify({username: currentUsername})], {type: 'application/json'})
);
```

- O cookie `tlm_access_token` já é HttpOnly/SameSite=Strict e acompanha o beacon na mesma origem;
  portanto o backend consegue identificar o usuário sem expor token no body.
- Beacon é best-effort: se o navegador não enviar, o monitoramento pode continuar até a próxima
  desconexão explícita. Documentar essa limitação.
- Ao receber o beacon: `DetachAll/Detach` para o usuário autenticado + `PurgeOwnerMedia`.

### 5.1 Injeção de dependências

`controller.AppController` deve receber opcionalmente um `PixQueueService` via setter
(`SetPixQueueService`), seguindo o padrão de `SetMonitorManager`/`SetMessageCache`. Isso evita
refatorar o construtor atual e facilita testes.

`main.go` monta:

```go
wahaClient := whatsapp.NewClient(whatsapp.LoadConfigFromEnv())
mediaStore := media.NewMinIOStorage(media.LoadConfigFromEnv())
pixSvc := controller.NewPixQueueService(repo, wahaClient, mediaStore)
ctrl.SetPixQueueService(pixSvc)
```

Não haverá worker de expurgo por TTL. A regra de expurgo passa a ser por usuário autenticado:

```go
func (c *AppController) DetachMonitoring(ownerUserID, username string) ([]string, error) {
    lives, err := c.monitorAttachments.Detach(ownerUserID, username)
    if err == nil && c.pixQueue != nil && ownerUserID != "" {
        go c.pixQueue.PurgeOwnerMedia(ownerUserID, "live disconnected")
    }
    return lives, err
}
```

Detalhes obrigatórios do hook:

- `handleDisconnect` e o beacon extraem `ownerUserID` via `auth.UserFromContext(r.Context())`.
- `username` vazio desanexa o usuário de todas as lives dele, mas nunca remove outros usuários.
- `PurgeOwnerMedia` nunca recebe lista de usuários nem executa delete global.
- Falha de expurgo não altera o resultado da desconexão; apenas loga.

## 6. MinIO

### 6.1 SDK

Adicionar dependência Go:

```text
github.com/minio/minio-go/v7
```

O pacote `internal/media` encapsula o SDK para manter o domínio independente.

### 6.2 Bucket e chaves

- Bucket default: `tlm-pix-media`, configurável por `MINIO_BUCKET`.
- Chave: `pix-media/{ownerUUID}/{messageUUID}.{jpg|pdf}`.
- Content-Type whitelist:
  - `image/jpeg`
  - `application/pdf`
- No boot, o backend tenta garantir o bucket (`BucketExists`/`MakeBucket`). Se MinIO estiver
  indisponível, o backend continua subindo para manter texto/fila operacionais, mas a ingestão de
  comprovantes deve falhar com erro claro até o MinIO voltar.
- Sem presigned URL no frontend nesta fase: o backend lê o objeto do MinIO e devolve bytes em
  `GET /api/pix/media/{messageId}`. Isso mantém auth simples e evita expor endpoint público.
- Se o volume crescer, a evolução natural é trocar esse endpoint por redirect 307 para URL
  assinada curta.

### 6.3 Upload inbound

Fluxo:
1. Webhook validado/parseado.
2. WAHA download (`payload.media.url`) → bytes.
3. Validação MIME real por magic bytes:
   - JPEG: prefixo `FF D8 FF`;
   - PDF: prefixo `%PDF-`.
4. `PutObject` no MinIO com tamanho e content-type explícitos.
5. Inserir linha em `pix_messages` com `media_path` = object key.
6. Se o insert falhar, tentar remover o objeto recém-criado (best effort) para evitar órfãos.

### 6.4 Expurgo por desconexão

`PixQueueService.PurgeOwnerMedia(ownerUserID, reason string)`:

1. Exige `ownerUserID` não vazio; sem dono, não executa.
2. Lista no banco mensagens com:
   `owner_user_id = $ownerUserID AND media_path IS NOT NULL AND media_deleted_at IS NULL`,
   em lotes de 100.
3. Para cada objeto:
   - `RemoveObject(bucket, media_path)`;
   - erros "NoSuchKey" são idempotentes/OK;
   - marca `media_deleted_at = now()`, `media_delete_reason = reason`.
4. Logs agregados: quantidade removida/falhas; nunca logar conteúdo, número do cliente ou chave
   completa se não for necessário.
5. Chamado após a desconexão da live pelo usuário autenticado.
6. Não purgar no boot: reinício do backend não é desconexão de live.

Endpoint de mídia:
- se `media_deleted_at IS NOT NULL` → `410 Gone`;
- se objeto sumiu mas flag não foi marcada → marca best effort e retorna `410`;
- UI mostra “Comprovante removido ao desconectar a live”.

## 7. Modelo de dados

Convenções:
- IDs `BIGSERIAL PRIMARY KEY` → Go `int64`.
- `owner_user_id TEXT NOT NULL` (UUID do Supabase Auth), **sem FK para `auth.users`**, para manter
  compatibilidade com o Postgres local do docker-compose.
- Integridade do owner é garantida pela aplicação (usuário autenticado); o banco não precisa
  conhecer o schema Supabase.
- Timestamps `TIMESTAMPTZ`, scan via `sql.NullString`.
- SQL idempotente em `migratePostgres()` + arquivo `supabase/migrations/005_pix_queue.sql`.
- RLS default deny nas 4 tabelas; REVOKE só no arquivo SQL.

Erros sentinelas novos: `ErrPixNotFound`, `ErrPixForbidden`, `ErrPixInvalidTransition`.

## 8. API REST

Todas as rotas `/api/pix/*` exigem auth e resolvem `ownerUserID := auth.UserFromContext(r.Context()).ID`.
Com `AUTH_ENABLED=1`, `ownerUserID` vazio deve falhar como `401`.

### 8.1 Monitoramento multiusuário

Rotas novas/alteradas:

| Método/rota | Regra |
|---|---|
| `POST /api/monitoring/attach` `{username}` | Anexa o usuário autenticado à live; se for o primeiro usuário, inicia o monitor |
| `POST /api/monitoring/beacon-disconnect` | Beacon de `pagehide`; autenticado por cookie; desanexa o usuário e dispara expurgo dele |
| `GET /api/disconnect` existente | Passa a chamar detach por usuário, preservando compatibilidade |

### 8.2 Pairing WhatsApp

| Método/rota | Resposta |
|---|---|
| `POST /api/pix/whatsapp/connect` | `200 {sessionName,status}` — cria/reativa sessão |
| `GET /api/pix/whatsapp/qr` | `200 image/png` ou `409 {error:"already_connected"}` |
| `GET /api/pix/whatsapp/status` | `200 {status,connected,mePhone,sessionName}` |
| `POST /api/pix/whatsapp/disconnect` | `200 {success:true}`; atualiza status local |

Se WAHA não estiver configurado/disponível: `503 {error:"whatsapp_unavailable"}`.

### 8.3 Fila, conversa e histórico

| Método/rota | Regra |
|---|---|
| `GET /api/pix/tickets?status=pending\|answered&limit=` | Default `pending`; pendente ordena FIFO (`received_at,id`), respondido ordena `answered_at DESC` |
| `GET /api/pix/tickets/{id}/messages?limit=` | Somente dono; retorna mensagens ASC |
| `POST /api/pix/tickets/{id}/messages` | Body JSON `{body}`; somente texto; ticket deve estar `pending` |
| `POST /api/pix/tickets/{id}/answer` | Marca respondido; idempotente (`200` se já respondido) |
| `GET /api/pix/contacts/{id}/history?limit=` | Tickets passados daquele contato |
| `GET /api/pix/media/{messageId}` | 200 com bytes do MinIO; `410` se apagado; `404` se não existir/não for do dono |

`POST /messages` deve validar:
- `Content-Type: application/json`;
- body até ~4.000 caracteres;
- `ticket.status == pending`;
- contato do ticket tem `whatsapp_jid` válido.

Resposta de envio:

```json
{"success":true,"messageId":123,"whatsappMessageId":"false_5511..."}
```

### 8.4 Webhook público

`POST /api/webhooks/whatsapp`

- Adicionar em `auth.PublicPath`.
- Ler raw body antes de `json.Decode` para validar HMAC.
- Responder rápido:
  - `401` assinatura inválida;
  - `200 {"received":true,"ignored":true}` para `fromMe`, grupo, ack ou sessão desconhecida;
  - `200 {"received":true,"ticketId":...}` em processamento OK;
  - `500` somente em falha interna real.
- Não incluir dados sensíveis no response/log.

## 9. Fluxos detalhados

### 9.1 Pairing

1. Frontend chama `POST /api/pix/whatsapp/connect`.
2. Backend garante sessão WAHA e upsert em `pix_whatsapp_sessions`.
3. Frontend busca QR e faz poll de status a cada 3s.
4. Ao conectar, backend persiste `status='connected'`, `me_phone`, `me_jid`, `connected_at`.
5. UI exibe número conectado e habilita a fila.

### 9.2 Inbound

1. WAHA envia webhook.
2. HMAC validado; envelope parseado.
3. `session` → `pix_whatsapp_sessions.session_name` → `owner_user_id`.
4. Upsert contato por `(owner, whatsapp_jid)`.
5. Se não houver ticket `pending`, criar; senão reutilizar o pendente.
6. Texto:
   - salva `type='text'`, `body`.
7. Comprovante JPG/PDF:
   - baixa `payload.media.url`;
   - valida MIME real;
   - faz `PutObject` no MinIO;
   - persiste mensagem com `media_path`, `media_mime` e `media_filename` sanitizado;
   - marca `has_receipt=true` no ticket.
8. Falha de MinIO/download:
   - não salvar uma linha fingindo ter comprovante;
   - persistir como `type='unsupported'`, com body técnico curto (`[comprovante indisponível]`);
   - registrar log e permitir resposta automática para orientar reenvio.
9. Não suportado:
   - salva `type='unsupported'`;
   - se `auto_reply_sent_at IS NULL`, envia texto automático e marca a coluna.
10. Atualiza `last_message_at` e emite SSE.

SSE:

```text
event: pix-ticket-update
data: {"ownerUserId":"...","ticketId":123,"contactId":45}

event: pix-new-message
data: {"ownerUserId":"...","ticketId":123,"messageId":987}
```

Não enviar corpo da mensagem no SSE; frontend busca pela API.

### 9.3 Outbound

1. Handler valida ownership/status/texto.
2. `sendText` para `contact.whatsapp_jid`.
3. Persistir outbound **após** sucesso 2xx do WAHA.
4. Se WAHA não devolver id, usar `waha-local-<uuid>`.
5. Broadcast SSE `pix-new-message`.

### 9.4 Respondido

1. `POST /answer` exige dono e ticket pendente.
2. `status='answered'`, `answered_at`, `answered_by`.
3. Item sai da fila e aparece no histórico.
4. Nova mensagem futura do mesmo contato cria novo ticket pendente.

### 9.5 Expurgo ao desconectar a live ou fechar a página

1. `handleDisconnect` extrai o usuário autenticado.
2. O usuário é desanexado da(s) live(s) dele via `DetachMonitoring`.
3. Se nenhum outro usuário estiver conectado na live, o monitor interno é encerrado.
4. Depois do detach, dispara `PurgeOwnerMedia(ownerUserID, "live disconnected")` em goroutine.
5. O serviço remove apenas os objetos ativos daquele usuário e marca as linhas correspondentes.
6. Falhas são logadas e não bloqueiam a desconexão da live.

Fechamento da página:

1. Frontend envia beacon autenticado em `pagehide`.
2. Backend valida o cookie `tlm_access_token`, identifica o usuário e executa o mesmo detach/expurgo.
3. Se o usuário tiver a mesma conta aberta em duas abas, fechar uma delas desconecta a live dela
   inteira e apaga suas mídias; controle por aba fica fora do escopo.

## 13. Segurança

- Webhook público com HMAC-SHA512 fail-closed.
- Beacon de desconexão não fica em `PublicPath`: ele passa pelo middleware e depende do cookie
  `tlm_access_token` HttpOnly/SameSite=Strict.
- Nenhum dado de cliente no payload SSE.
- Ownership em todas as queries (`owner_user_id`).
- `answered` bloqueia novos envios do operador até que nova mensagem crie novo ticket.
- MIME real validado por magic bytes antes de salvar.
- Limites: webhook 1 MiB; download WAHA 16 MB; texto operador 4.000 caracteres.
- Logs não devem conter `WAHA_API_KEY`, credenciais MinIO, assinatura HMAC, conteúdo de
  comprovante ou corpo de mensagens.
- MinIO não exposto publicamente; todo acesso via backend autenticado.
- RLS default deny + REVOKE no SQL; backend segue como papel com bypass de RLS.

## 18. Riscos e mitigações

| Risco | Mitigação |
|---|---|
| WAHA quebrar em mudança do protocolo WhatsApp Web | Imagem pinada por engine; atualização manual controlada |
| Usuários múltiplos no mesmo WAHA | Sessões separadas `pix_<uuid>`; monitorar limite prático; avaliar WAHA Plus depois |
| Mídia não baixar por URL `localhost` | `WAHA_BASE_URL=http://waha:3000` fixo no compose |
| Contato `@lid` sem número | Preservar JID para resposta; resolver `pn` best-effort |
| Duplo envio por resposta WAHA sem id | Persistir com `waha-local-*` após 2xx |
| Falha parcial ao apagar MinIO | Delete idempotente + marcação no banco; logs agregados |
| Um usuário sair e derrubar a live de outro | Attach/detach por `owner_user_id`; monitor interno só para quando não restar usuário conectado |
| Fechamento de aba não enviar beacon | Beacon é best-effort; documentar limitação e manter botão Desconectar como caminho confiável |
| Recarregar página disparar expurgo | Detectar `navigation.type === 'reload'` e não enviar beacon |
| Backend reiniciar sem desconectar live | Não purgar no boot; mídias permanecem até próxima desconexão |
| Vazamento via SSE | Eventos carregam apenas IDs; conteúdo sempre via API autenticada |
| MinIO exposto por engano | Não publicar portas em produção; só rede Docker interna |
| Auth desabilitado (`AUTH_ENABLED=0`) | Dev-only; documentar que a Fila PIX deve ser usada com auth real |

## 19. Critérios de aceite

- Cada usuário pareia seu WhatsApp sem intervenção manual em curl.
- Cliente envia texto/JPG/PDF e aparece na fila do usuário correto.
- Comprovantes são armazenados no MinIO.
- Ao desconectar a live ou fechar a página, somente os comprovantes daquele usuário são removidos
  do MinIO.
- Se dois usuários monitoram a mesma live, a saída de um não remove mídias do outro nem derruba o
  monitoramento enquanto houver usuário conectado.
- Recarregar a página não dispara expurgo.
- Operador responde somente texto pela UI.
- Clicar Respondido remove da fila e move o número para o histórico.
- Conversa e histórico permanecem após a remoção das mídias.
- Webhook inválido retorna 401.
- Todos os testes Go/frontend existentes e novos passam.
- `docker compose up -d --build` sobe backend, frontend, Postgres, WAHA e MinIO juntos.
