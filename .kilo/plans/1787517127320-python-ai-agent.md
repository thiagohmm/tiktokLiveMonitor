# Plano: Agente de IA em Python (copiloto + resumo da live)

## Objetivo

Adicionar um **agente de IA em Python** (serviço standalone) que roda junto com o monitor Go e usa o **llama-server local** já gerenciado pelo Go (porta 8080, endpoint OpenAI-compatível). O agente tem duas capacidades:

1. **Resumir/analisar a live** em tempo real, incluindo **repetições de mensagens**.
2. **Copiloto do streamer** com ferramentas (consultar ranking, perfil de usuário, presentes, histórico de moderação, estado, relatório).

## Decisões (confirmadas com o usuário)

- Serviço **Python standalone**, desacoplado do monitor Go.
- Usa o **llama-server local** já existente (não sobe outro); consome `POST /v1/chat/completions`.
- **Dados**: assina o SSE `/events` (mensagens, presentes, `REPETICAO`, correlações) + chama as APIs REST existentes sob demanda.
- **Interface**: painel novo na web UI atual (`web/`), que chama a API HTTP do agente.
- **Start**: o Go **spawna o subprocesso Python** sempre (local e Docker). `go run main.go` sobe o agente automaticamente.
- **Docker**: adiciona Python + dependências do agente à imagem (um único container; sem serviço compose separado).

## Arquitetura

```
web (painel "Agente")
   │  fetch /agent/ask, /agent/summarize  (same-origin)
   ▼
Go server (:3001)
   ├─ /events  (SSE)  ──────────────► agent (subprocesso Python, :9001)
   ├─ /api/*   (REST) ◄── httpx ──────   agent chama REST quando precisa
   └─ /agent/* (reverse proxy) ─────►   agent HTTP API (FastAPI)
                                            └─ llama-server (:8080) via httpx
```

- `agent/` (novo, Python): buffer de mensagens/presentes/repetições, cliente LLM, tools REST, router, API HTTP.
- `internal/agent/` (novo, Go): gerencia o lifecycle do subprocesso Python (análogo a `internal/ai` com o llama-server).
- `internal/view/server.go`: rota de reverse proxy `/agent/*`.
- `web/index.html` + `web/renderer.js`: painel novo.
- `Dockerfile`: Python + `pip install` das deps.

## Portas / variáveis de ambiente

| Variável      | Default                    | Uso                                   |
|---------------|----------------------------|---------------------------------------|
| `AGENT_PORT`  | `9001` (bind `127.0.0.1`)  | Porta HTTP do agente                  |
| `MONITOR_URL` | `http://127.0.0.1:3001`    | SSE + REST do monitor                 |
| `LLM_URL`     | `http://127.0.0.1:8080/v1` | llama-server (chat completions)       |

O Go define essas variáveis ao spawnar o subprocesso (usa os mesmos host/porta que já gerencia para o llama-server). Se Python não existir no host, o Go loga aviso e a aplicação segue sem o agente (degradação graciosa); o painel mostra "agente indisponível".

## Tarefas do agente (ordem de execução)

### 1. Estrutura do agente Python — `agent/`
- `agent/__main__.py` (entrypoint `python3 -m agent`), `agent/__init__.py`.
- `requirements.txt`: `fastapi`, `uvicorn`, `httpx` (sem SDK OpenAI, sem LangChain — ver Riscos).
- Módulos: `config.py` (env), `llm.py`, `sse.py`, `buffer.py`, `tools.py`, `router.py`, `summary.py`, `api.py`.

### 2. Cliente LLM — `agent/llm.py`
- `chat(messages, max_tokens)` → `POST {LLM_URL}/chat/completions` com `{"messages":..., "temperature":0.1, "stream":false, "chat_template_kwargs":{"enable_thinking":false}}`.
- Timeout generoso (ex.: 120s, igual ao Go) e retry simples com backoff quando o llama-server ainda não está pronto.

### 3. Consumidor SSE + buffers — `agent/sse.py`, `agent/buffer.py`
- Conectar em `{MONITOR_URL}/events` (httpx stream), com **reconexão automática** com backoff (o agente pode subir antes do servidor Go escutar).
- Filtrar eventos de interesse: `chat`, presentes (`gift`/`new-gift-user`), `flagged-message` (categoria `REPETICAO`), `suggested-response`, correlação.
- `buffer.py`: anel de mensagens (limite ~500, como `chatBufferMax`), contadores de presentes, e **detecção de repetição** espelhando a regra do Go (`monitor.go:616`): mesmo `uniqueId` + texto normalizado igual dentro de 60s (`repeatWindowMs`), alerta na 3ª ocorrência (`repeatsRequired`). Guardar também o nickname para resolver menção→uid.

### 4. Tools (wrappers REST) — `agent/tools.py`
Funções assíncronas que chamam as APIs existentes via httpx:
- `ranking(live)` → `GET /api/ranking?live=`
- `profile(uid)` → `GET /api/profile?uid=` (resolver nickname→uid pelo buffer)
- `gifts(user?)` → `GET /api/gifts?user=` ou sem user
- `history()` → `GET /api/history`
- `state()` → `GET /api/state`
- `report(live)` → `GET /api/report?live=`
- `pinned()` → `GET /api/pinned-comments`
- `target_gifts(pending=true)` → `GET /api/target-gift-history?pending=1`

### 5. Router do copiloto — `agent/router.py`
- Recebe o comando do streamer; decide entre responder direto (buffer) ou chamar uma tool.
- **Prompt de roteamento** que pede ao LLM uma linha tipo `TOOL:ranking` / `TOOL:profile:uid` / `NONE`, com **fallback determinístico** por palavras-chave (ex.: "ranking", "perfil de X", "presentes", "moderação", "resumo") quando a saída do modelo for inválida (modelo pequeno é instável em tool-calling).
- Fluxo: rotear → executar tool → montar contexto (resultado da tool + resumo do buffer) → pedir a resposta final ao LLM (português-BR, conciso).

### 6. Resumo da live — `agent/summary.py`
- Monta contexto a partir do buffer: nº de mensagens, participantes ativos, **mensagens repetidas** (texto + contagem + autor), presentes, eventos flagados/moderação.
- Chama o LLM para produzir resumo estruturado com seção "Repetições".
- Opcional: mesclar com `GET /api/report` quando a live terminar.

### 7. API HTTP do agente — `agent/api.py`
- `GET  /agent/health` → `{"ok":true, "llm":bool, "sseConnected":bool}`
- `POST /agent/ask` → `{question}` → `{answer}`
- `GET  /agent/summarize` → `{summary}` (ou `POST /agent/ask` com intenção de resumo)
- CORS não é necessário (o Go faz proxy same-origin).

### 8. Go: spawn do subprocesso — `internal/agent/agent.go` + `main.go`
- `agent.Manager`: `Start()` localiza `python3`/`python`, monta `python3 -m agent` com env (`AGENT_PORT`, `MONITOR_URL`, `LLM_URL`), `cmd.Dir` = raiz do repo, redireciona stdout/stderr para os logs, reapa com `cmd.Wait()` e `Stop()` mata no shutdown (mesmo padrão de `internal/ai`).
- `main.go`: cria o manager, inicia após o servidor HTTP (ou antes, com retry do agente no SSE), `defer Stop()`.
- Se Python ausente → loga aviso e segue sem agente (não fatal).

### 9. Go: reverse proxy — `internal/view/server.go`
- Rota `/agent/` usando `httputil.NewSingleHostReverseProxy` para `http://127.0.0.1:<AGENT_PORT>` (registrar via `http.StripPrefix("/agent", ...)`).
- Se o agente não estiver de pé, retorna 502 (o painel trata).

### 10. Painel na web UI — `web/index.html` + `web/renderer.js`
- Nova seção "Agente" com: caixa de texto para comando (copiloto), botão "Perguntar", botão "Resumir live", e área de resposta.
- `renderer.js`: `fetch('/agent/ask', {method:'POST', body:{question}})` e `fetch('/agent/summarize')`; estados "Pensando..."/erro; tratar 502 como "agente indisponível".
- Reaproveitar o padrão visual existente (mesmos estilos de "Pergunta para IA").

### 11. Dockerfile
- No stage `debian:trixie-slim`, adicionar `python3` + `python3-pip`/venv e `COPY agent/ ./agent/` + `COPY requirements` e `pip install -r requirements`.
- Ajustar `EXPOSE`/healthcheck se necessário (o agente escuta em 127.0.0.1, alcançado via proxy do Go).

### 12. Testes e validação
- Testes Python: `buffer` (detecção de repetição), `router` (fallback de roteamento), mock do LLM/REST.
- Teste Go: manager spawn (skip se Python ausente) e proxy.
- `go build ./...` e `go test ./...`.

## Validação manual

1. `go run main.go` → log mostra o agente subindo (`python3 -m agent`), sem passos extras.
2. `curl http://127.0.0.1:3001/agent/health` → `{"ok":true,...}`.
3. Conectar numa live; `curl http://127.0.0.1:3001/agent/summarize` → resumo com seção de repetições.
4. `curl -XPOST http://127.0.0.1:3001/agent/ask -d '{"question":"ranking da live"}'` → ranking via tool.
5. Na UI: painel "Agente" responde e mostra "Pensando..." corretamente.
6. Enviar a mesma mensagem 3x na live → o resumo lista a repetição.
7. Docker: `docker compose build && docker compose up` → agente funciona dentro do container.

## Riscos / observações

- **Modelo local** passa a ser `gemma-4b` (Unsloth, 4B/Q4_K_M): melhor que o 2B anterior, mas ainda pequeno para resumos/copiloto longos — manter saídas curtas e prompts enxutos.
- **Remoção da variante Docker E2B** (não existe no repo Unsloth): Docker/Pi passa a usar o mesmo GGUF de 4B (~5 GB). Pi 4 de 1–2 GB pode não comportar; ajustar `LLAMA_SHM_SIZE` (`.env.example`) e considerar hardware com mais RAM.
- **Tool-calling instável em modelo pequeno** → router com fallback determinístico (não depender de function-calling nativo).
- **Python ausente no host** → degradação graciosa (app roda sem agente).
- **Imagem Docker maior** (Python + deps) e build mais lento na Pi; mitigável com `--no-cache-dir` no pip.
- **Reconexão SSE** e ordem de startup (agente pode subir antes do servidor Go) → retry com backoff.
- Segurança: há um token Bearer hardcoded em `.blackboxcli/settings.json` (fora do escopo deste plano, mas recomendo remover/rotacionar e adicionar ao `.gitignore`).
